## Observed baseline and host contract

A generated Node browser fixture failed before production edits: a Mac advertising
`sessionOps` produced a row with no More action. No customer data was inspected.
Current `RemoteCommands` accepts close, rename and archive; rename trims input,
allows an empty reset and limits UTF-8 to 80 bytes. `archiveFromRemote` archives
the saved conversation and closes its matching open tabs. These host files are
unchanged by this ticket.

## Behavior and boundaries

- Capable rows show provider/folder metadata and a separate 44px More button.
  Hosts without `sessionOps` keep their previous rows and expose no new actions.
- Rename respects the provider capability, validates UTF-8 length and control
  characters, and permits an empty name. Archive requires `canArchive === true`
  and a provider archive capability that is not false.
- Close and archive always ask first. Working and uncertain activity has an
  explicit stopping warning. A change in activity class requires a new
  confirmation; the host's multi-tab archive effect is identified in the copy.
- The captured row's id, optional provider/native session/cwd, paired credential,
  Mac and connection/command/page identity must still match. The existing queue
  holds a fresh state read and the write together; checks repeat immediately
  before dispatch and after sealing. Selection is never substituted for the row.
- A rejected rename preserves the field and refreshes state before retry. A
  newer observed host name blocks the retained edit. An unavailable refresh
  explains why retry is disabled. Missing replies never replay writes after a
  reconnect. Replies update the host-owned state; there is no optimistic rename.

The host does not offer an atomic conditional-rename/revision token. Fresh-read
checks reject changes the client observes; another client can still change the
name after that read. This bounded client change does not claim host-side atomic
conflict protection or change the protocol.
