# REA-1205: web session actions

Base: `9165c2d430aaf378f48bbc7732675bc9dfa1a5b5`.

## Observed baseline and host contract

A generated Node browser fixture failed before production edits: a Mac advertising
`sessionOps` produced a row with no More action. No customer data was inspected.
Current `RemoteCommands` accepts close, rename and archive; rename trims input,
allows an empty reset and limits UTF-8 to 80 bytes. `archiveFromRemote` archives
the saved conversation and closes its matching open tabs. These host files are
unchanged by this ticket.

## Behavior and boundaries

- Capable rows show provider/folder metadata and a separate 44px More button.
  Hosts without `sessionOps` keep their previous rows and expose no new actions.
- Rename respects the provider capability, validates UTF-8 length and control
  characters, and permits an empty name. Archive requires `canArchive === true`
  and a provider archive capability that is not false.
- Close and archive always ask first. Working and uncertain activity has an
  explicit stopping warning. Any observed change in activity class permanently invalidates that confirmation,
  even if activity returns to its prior class. Archive always warns that it stops
  all open tabs for the conversation, including working and unknown sessions;
  it does not guess the host-owned affected set from incomplete client rows.
- The captured row's id, optional provider/native session/cwd, paired credential,
  Mac and connection/command/page identity must still match. The existing queue
  holds a fresh state read and the write together; checks repeat immediately
  before dispatch and after sealing. Selection is never substituted for the row.
- A rejected rename preserves the field and refreshes state before retry. A
  newer observed host name blocks the retained edit. A capability loss also
  invalidates the open form with an explanatory cancel/reopen message. An unavailable refresh
  explains why retry is disabled. Missing replies never replay writes after a
  reconnect. Replies update the host-owned state; there is no optimistic rename.

The host does not offer an atomic conditional-rename/revision token. Fresh-read
checks reject changes the client observes; another client can still change the
name after that read. This bounded client change does not claim host-side atomic
conflict protection or change the protocol.

## Review findings and revision

The automatic review on initial head `270c385` found four defects. Seven new
focused cases reproduced them before production fixes. The revision:

- [Locks dismissal after dispatch](https://github.com/gl11tchy-team/sigil/pull/187#discussion_r4307414428): Cancel and Escape work before the write is sent; afterward they cannot imply that the Mac operation was canceled. The pending action reads Saving/Archiving/Closing until its reply or timeout.
- [Warns across archive's full scope](https://github.com/gl11tchy-team/sigil/pull/187#discussion_r4307414430): the warning is unconditional because matching tabs may be working, use path aliases, or be absent from the capped snapshot. No client-side cwd matching is added. A synthetic idle copy plus a working copy proves the warning and both-tab effect.
- [Explains capability loss](https://github.com/gl11tchy-team/sigil/pull/187#discussion_r4307414432) on the open form while preserving edits; reopening is required even if support later returns.
- [Latches activity changes](https://github.com/gl11tchy-team/sigil/pull/187#discussion_r4307414434) until the dialog is explicitly reopened. An idle/working/idle oscillation cannot revive an old confirmation.

matching parents/tree. It certifies that initial revision only. The revised head
needs its own required CI. Existing review threads remain for parent personal
