## Boundary and artifact transfer

- Default repository contents permission is read-only. A job-level same-repo
  PR condition rejects fork PRs before allocating the owner's runner.
- Both checkouts disable persisted credentials. A presence-only check rejects
  a leftover local HTTP auth header without printing its value.
- Verification retains its existing tests, diagnostics, universal build,
  actual-bundle smoke and zip gates. It records ZIP digest/size and
  repository/SHA/run/attempt metadata after those gates.
- Each successful verification uploads Sigil.zip and release.json with
  seven-day retention. The artifact name includes run ID and producing
  attempt, so reruns need not overwrite an earlier immutable artifact.
- The main-push-only release job needs verification and alone grants
  contents:write. It checks out that run's exact SHA without persisting auth,
  downloads the producing artifact ID from job outputs in the same run,
  and checks its ZIP against independent digest/size outputs plus the
  manifest's repository, SHA, event/ref, run and attempt.
- The release job executes only the checked-out main publisher. It neither
  builds nor executes code from the downloaded artifact. PRs and manual
  dispatches retain downloadable artifacts and never publish.

The transfer uses the documented [v4 artifact ID/current-run inputs](https://github.com/actions/download-artifact/blob/v4/README.md)
and [immutable artifact outputs](https://github.com/actions/upload-artifact/blob/v4/README.md).
GitHub grants token permissions at [workflow/job scope](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token);
omitting an explicit token environment variable alone would not remove access.
Runtime artifact/cache capabilities remain distinct from repository contents
permission.

## Publication and retry semantics

The publisher keeps the existing build-number/attempt tag family and
create-then-prune policy. Its tag uses the artifact's verification attempt:
a release-only rerun does not create a new tag merely because the release
job's attempt increased. A new verification attempt gets a new artifact/tag.

Before mutation it verifies that main still names the source, lists releases
including drafts, and rejects tag collisions and any numerically newer build
release. Pruning is limited to strictly older build numbers/attempts (and the
legacy latest tag), including after the post-create readback. An older
producing artifact cannot replace or prune a newer attempt for the same SHA.
An existing complete release
must match its title, full provenance notes, tag SHA and uploaded ZIP
digest/size. A match is reused. Mismatched, partial or draft state fails
closed and is preserved for diagnosis; automatic destructive repair is not
implemented.

Parent review identified the older-producing-attempt case after the opening
review. An offline reproduction at the original head recreated build-12.1
and deleted build-12.2 despite identical source SHA. The regression now
preserves both release states without mutation. GitHub documents
[specific-job reruns with the original SHA/ref](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs)
and a [job-ID rerun endpoint](https://docs.github.com/en/rest/actions/workflow-runs#re-run-a-job-from-a-workflow-run).
Historical-job producer-output selection has not been live-tested; the helper
rejects the stale state without assuming the service makes it unreachable.

[gh release create is non-atomic](https://cli.github.com/manual/gh_release_create):
an error can follow a successful publication. The helper reads back that
uncertain result once and accepts only a complete match, never issuing a
second create. Old build cleanup runs only after verified publication,
preserving the existing tag filter and unrelated releases.

Manifest/ZIP sizes, API pagination, per-command time and total operation
time are bounded. The current private release channel remains authenticated;
anonymous download availability is REA-1197, not a claim of this change.
