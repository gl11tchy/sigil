## Behavior and regression coverage

`ProviderInstallation.timedOut` distinguishes deadline expiry from an executable
that is missing, invalid or cannot start. A timeout never authorizes launch.

`ProviderChecks` owns one cancellable timer for all providers, with the same
clock/probe generation fences as entry/Settings checks. It retries only typed
timeouts with 5/15/45-second delays between attempts (normally t+5, t+20, t+65
after a timeout, excluding probe duration). The next activation may advance one
pending attempt; bursts do not reset the three-attempt budget. Missing/invalid
failures receive no automatic retries. An exhausted timeout says “Version check
timed out” and provides Check Again through the existing New Session tile or
Grok Settings check. Explicit checks start a new bounded sequence.

Every current completed batch notifies AppModel. A ready saved prefix restores
without opening New Session; a later success cannot overtake an earlier pending
retry. Deferred references keep their saved positions/selection through
exhaustion, and a later successful explicit check inserts the recovered tab
before later restored peers. Existing identity comparisons remain unchanged.

CI-only `ProviderLaunchAvailabilityTests` inject the actual probe, clock and
sleep scheduling, including delivery of canceled timers, to cover:

- One timeout followed by success restoring a saved native tab.
- Exact backoff, exhaustion, truthful state and one-click manual recovery.
- No automatic retry of missing/invalid installations.
- Forced refresh and executable change during waiting and running retries.
- Activation bursts without duplicate probes or renewed budgets.
- Two providers completing separately, in either order, including exhaustion,
  manual recovery, exact/legacy selection and repeated restoration calls.

Kit tests cover synchronous/asynchronous timeout flags, missing/invalid failure
classification and launch rejection for a contradictory timeout result.
Ordinary exact-head CI results are recorded on the ticket's PR. No native
AX/layout, actual cold-login timing, customer CLI/version or runtime impact is
claimed.

## PR148 review remediation

The parent confirmed two source defects at `d13ac91`: restarting a restored
peer dropped its saved-order rank, and ordinary inventory refresh replenished
an exhausted timeout budget. Replacement construction now transfers the old
rank to the new tab ID. Routine refresh skips every existing recovery sequence,
including exhaustion; an explicit selected-provider Check Again/start check
resets only that provider. The exhaustion test exercises repeated entry,
actual remote Options and a different provider's explicit check before manual
Codex recovery. The two-provider test restarts the restored peer in all four
exhaustion cases, covering both saved positions and exact/legacy selection.

The view-only activation subscription was confirmed by source inspection.
Recovery now runs in `appDidBecomeActive`, the existing app-wide delegate hook.
A CI test creates a Settings-style Grok check and calls that model hook without
constructing RootView/WindowContent. This verifies scheduling, not native window
closure/AX behavior.

Four bounded synthetic child-spawning probes reproduced descendants surviving
the original direct-PID timeout kill. A group-only candidate stopped ordinary
children across sh/zsh/bash but failed a synthetic Foundation child with its own
group. The final cleanup freezes a bounded owned tree, enumerates only child
PIDs, fences signals by UID/parent/kernel birth identity, kills leaves and the
isolated root group, and confirms the direct process exit within a bounded wait.
The walk is capped at 64 processes and 250 ms; direct exit gets another 250 ms.
Incomplete cleanup is an ordinary unavailable failure, never an automatically
retryable timeout. No process arguments/open files or personal data are read;
deliberately detached/reparented daemons are not inferred from the inventory.

Native production-source checks cover 13 shell probes including bash job-control
groups, a separate-group Foundation child, and the eight Kit classification
assertions. All use fixed three-second descendants, throwaway homes and owned
compiler caches. Each observed child/direct process was stopped after return.
Exact timings, source hashes and final CI outcomes are recorded on the PR.
CI Kit coverage adds eight child-cleanup cases across login shells, sync/async
detection and separate groups. AppModel and macro execution remain CI-only.
