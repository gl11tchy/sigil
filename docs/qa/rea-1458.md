# REA-1458: synchronize the Chats-close regression

Base: `cfddae6068f82f7b075e93df566d2a3110dd1262`.

## Controlled baseline

The unchanged Chromium target passed once locally (3.7 s). That pass does not
reproduce CI661/CI662. The original fixture records request receipt and waits
600 ms before replying; the test does not keep that response pending until Done
has completed its close handler. The exact pre-key assertion assumes it does.

A controlled baseline used the same relay, encryption, production assets and
exact `['a']` assertion. It held the first `a` reply while typing `lpha`, released
it **before Done**, and waited for the synthetic host to receive `alpha` before
closing the dialog and clicking Stop. Chromium then failed the original exact
assertion with `['a', 'alpha']`. This reproduces the CI symptom through the
missing in-flight assumption. Historical CI logs do not contain a response/close
trace, so this does not claim an observed trace from those runs or customer impact.
The temporary early-release control is outside the PR.

## Fixture contract

Only the first nonempty `a` search can use the new reply gate. Pairing, recent
chats and other requests retain the existing fixture behavior and delays.
Receipt is acknowledged after decryption, challenge validation and action
recording. Release is a separate operation; deadline expiry fails the fixture
and never releases it as a way to advance the test.

The regression holds `a` through remaining typing, the completed dialog `close`
event and Stop's click handler. Its acknowledgment listeners are installed after
the application handlers: `clearSaved()` has run before the close acknowledgment,
and the current interrupt handler synchronously calls `request`/`enqueue` before
the click acknowledgment. Neither handler nor application module is replaced.
Before release the test requires `a` still held, only `['a']` received, and no key
received. After release it requires the actual `key: interrupt` for tab `one`,
exact pre-key `['a']`, contiguous sequences, hidden error UI and no fixture/page
errors. Host challenge checks remain intact.

Two cases perform zero or three additional completed browser round trips before
Done and after key queuing. The host stays held across these bounded scheduling
variations. They use the original Done action; there is no elapsed sleep used as
a barrier. An exploratory Escape case did not produce the required dialog-close
event and is not claimed as coverage of the original Done contract.

Finally cleanup releases any held reply, removes the host message listener,
drains the existing serialized handler with a failure deadline, terminates the
owned synthetic socket and awaits its close event. The test asserts no held work,
a closed socket and no recorded errors after cleanup. The same cleanup executed
when the deliberate mutation failed the assertion.

## Limits and required CI

Local WebKit never reached this regression: both the original unmodified case
and gated prototypes stopped at the existing five-second Connected expectation,
after only the synthetic `pair` action, with `Connecting…` still shown. No local
WebKit pass or mutation sensitivity is claimed, and no timeout, permission,
browser version, retry or skip workaround was applied. A prototype that gated
all response timing was narrowed to the intended first `a` only; it is not the
final fixture contract. No production pairing diagnosis is claimed.

Normal exact-head CI must supply the WebKit and native results. Both scheduling
cases run in both configured engines as part of the unchanged browser gate.
Native SigilAppTests remain CI-only; no workflow ordering, gate, retry or skip
was changed. Actual final-head CI counts and existing skips belong on the PR.

repair pass does not establish its native baseline or implement REA-1240. Parent
